\title{Configurable Static Type Checking for Forth}
\author{Jaanus Pöial\\Tallinn University of Technology}
\date{}

\begin{document}
\maketitle

\begin{abstract}
Forth words exchange operands through a data stack, and Forth source may also
change the parser and dictionary while it is being read.  This paper describes
a configurable source-level checker for that setting.  The checker represents
a phrase by the stack cells it requires and the cells it leaves.  Each cell
has a profile-defined type and may have a symbolic identifier that records
value flow through words such as \texttt{DUP}, \texttt{SWAP}, and
\texttt{OVER}.

Straight-line code is checked by matching the output of one word with the
input of the next.  Branches are combined only when the implementation can
construct one common stack interface.  Repetition uses a finite test that
compares one pass with two passes.  The paper explains each algorithm with
source examples and pseudocode, including unequal branch depths and a loop
counterexample.  It also separates the implemented checks from stronger
claims: normalization can lose value-flow information, the current branch
operator is not a sound summary for every program, and the loop test does not
compute an inductive invariant.

The type hierarchy, primitive stack effects, parser words, defining words,
literals, and control structures are supplied in text files.  The native
implementation is \texttt{gforth-evaluator.fs}.  A complete artifact manifest
and reproducible example are included.  Comparisons with StrongForth,
pluggable Forth typing, and WebAssembly show which restrictions belong to this
prototype rather than to stack languages in general.
\end{abstract}

\noindent\textbf{Keywords:} Forth; static analysis; stack effect; type checking;
symbolic execution; concatenative languages.

\section{Introduction}

A Forth \emph{word} is a named operation.  Operands normally come from the
data stack instead of named parameters.  This paper writes the top of stack on
the right, following standard stack-effect notation:

\begin{lstlisting}
+   ( n1 n2 -- n3 )
\end{lstlisting}

The effect says that \texttt{+} consumes two numbers and produces one.  It
constrains only the visible top part of the stack; cells below that part remain
unchanged.  A colon definition introduces a new word:

\begin{lstlisting}
: SQUARED  ( n -- n*n ) DUP * ;
\end{lstlisting}

A conventional Forth system treats a stack effect as documentation.  The
comment may be missing, stale, or too weak to describe value flow.  For
example, the two results of \texttt{DUP} are copies of the same input.  A
checker also has to handle branches, loops, parser words, and words that extend
the dictionary while source is processed.

The evaluator in this project reads three inputs:

\begin{enumerate}
  \item a finite set of types, aliases, and subtype declarations;
  \item word effects plus parser and control-word metadata;
  \item the Forth source to check.
\end{enumerate}

It infers effects for source phrases and colon definitions without executing
the program.  An earlier Java implementation established the basic framework
\cite{poial2008}; the artifact studied here is the native Gforth version.  The
same engine can use a permissive profile that mostly checks stack depth or a
narrower profile that distinguishes numbers, flags, address classes, and
execution tokens.

The checker addresses four tasks beyond tokenization:

\begin{itemize}
  \item match adjacent stack interfaces in straight-line code;
  \item propagate types and value identities through stack shuffles;
  \item construct one interface for alternative control-flow paths;
  \item approximate repeated execution with a terminating local test.
\end{itemize}

These are design choices of this implementation.  They are not limitations of
concatenative languages as a class.  WebAssembly, for example, validates loops
against declared block interfaces, while StrongForth integrates typing into a
Forth system.  Section~\ref{sec:related} compares these alternatives.

\section{Analysis Model}
\label{sec:model}

\subsection{Profile-defined types}

A profile defines canonical type names, aliases, and subtype edges.  A typical
fragment is:

\begin{lstlisting}
type X cell x
type n number N
type char c
type addr a
type c-addr ca
type a-addr aa

rel n < X
rel char < n
rel addr < X
rel c-addr < addr
rel a-addr < c-addr
\end{lstlisting}

Here \texttt{X}, \texttt{cell}, and \texttt{x} are aliases.  The relation
\texttt{a-addr < c-addr} means that an aligned address is acceptable where a
character address is required.  The loader calculates transitive subtype
relationships, so it also knows that \texttt{a-addr} is an \texttt{addr} and
an \texttt{X}.

When two stack cells meet at a composition boundary, the checker applies a
simple rule:

\begin{itemize}
  \item if the types are equal, keep that type;
  \item if one type is a subtype of the other, keep the more specific type;
  \item otherwise, report a type clash.
\end{itemize}

The checker does not search for a third common subtype when the two boundary
types are unrelated.  This keeps matching deterministic but is less expressive
than full lattice-based subtyping.

\subsection{Stack effects and value identifiers}

A stack effect has an input side and an output side:

\begin{lstlisting}
( input cells -- output cells )
\end{lstlisting}

An arbitrary deeper prefix passes through unchanged.  For example,
\texttt{( n -- n )} can run on a stack containing other cells below the top
number.  Type-system literature sometimes calls that arbitrary prefix a
\emph{stack row}.  In implementation terms, it is simply a variable-length
prefix that the word does not inspect.

Types alone do not describe stack shuffles.  Square-bracket identifiers record
which positions carry the same symbolic value:

\begin{lstlisting}
DUP   ( X[1] -- X[1] X[1] )
SWAP  ( X[2] X[1] -- X[1] X[2] )
OVER  ( X[2] X[1] -- X[2] X[1] X[2] )
DROP  ( X -- )
\end{lstlisting}

Equal identifiers mean that the positions refer to the same abstract input.
Different identifiers do not assert that concrete values are unequal.  An
unindexed occurrence is treated as a fresh symbolic cell.  Before a word
effect is used, its identifiers are renamed so that separate word calls cannot
accidentally share variables.

The bracket notation is explicit internal notation.  Standard Forth prose
normally writes numeric suffixes, such as \texttt{n1 n2 -- n3}.  It omits the
suffix when all displayed items of that type denote one value, as in
\texttt{DUP ( x -- x x )}.  Section~\ref{sec:indices} returns to output
formatting.

\section{Checking Code Sequences}
\label{sec:sequence}

Suppose a checked prefix has one effect and the next word has another.  The
checker compares the first effect's output with the next word's input, starting
at the top of stack and moving toward deeper cells.

The implementation can be described by the following pseudocode.  Here
\texttt{replaceEverywhere} updates both input and output sides of both working
effects.

\begin{lstlisting}
compose(first, second):
    rename identifiers so the effects use disjoint names

    while first has an output and second has an input:
        actual   = top output of first
        expected = top input of second

        if actual.type and expected.type are unrelated:
            return TYPE_CLASH

        mergedType = the more specific boundary type
        mergedId   = a fresh identifier
        replaceEverywhere(actual, expected,
                          mergedType, mergedId)
        remove the matched output and input

    preserve any unmatched input requirement
    preserve any unmatched output result
    return the combined effect
\end{lstlisting}

The global replacement step is important.  If a boundary match refines an
\texttt{X} to \texttt{n}, every copy of that symbolic value must become
\texttt{n}.  Updating only the two boundary positions would lose information
carried through \texttt{DUP}, \texttt{SWAP}, or \texttt{OVER}.

When the first output becomes empty before the second input, the remaining
requirements of the second word become additional requirements of the whole
phrase.  They are placed below the requirements already inferred for the first
phrase.  When the second input becomes empty first, the unmatched output of
the first phrase is retained below the second word's results.  This states the
base cases directly and avoids ambiguous primed variables in the recursive
definition.

\subsection{Example: \texttt{1 2 + DUP}}

The individual effects are:

\begin{lstlisting}
1    literal integer  ( -- n )
2    literal integer  ( -- n )
+                     ( n n -- n )
DUP                   ( X[1] -- X[1] X[1] )
\end{lstlisting}

The reduction proceeds in four steps:

\begin{enumerate}
  \item \texttt{1} leaves one fresh \texttt{n}.
  \item \texttt{2} leaves a second fresh \texttt{n} above it.
  \item \texttt{+} consumes both numbers and leaves one new \texttt{n}.
  \item \texttt{DUP} accepts any \texttt{X}; matching refines that \texttt{X}
        to \texttt{n}, and replacement updates both copies.
\end{enumerate}

The inferred phrase effect is:

\begin{lstlisting}
( -- n[1] n[1] )
\end{lstlisting}

The native trace exposes the same steps:

\begin{lstlisting}
1    ( -- n )
2    ( -- n )
+    ( n n -- n[1] )
DUP  ( n[1] -- n[1] n[1] )
< n[1] n[1]
\end{lstlisting}

For fixed identifier-renaming rules, this algorithm is deterministic.  Another
implementation may choose different identifier numbers, but consistent
renaming does not change the data-flow relationships.

\section{Internal Identities}
\label{sec:indices}

Internal analysis and user-facing formatting have different requirements.
The analyzer should retain every known identity relationship.  The printer
should use consecutive suffixes in the standard Forth style.

For example, the internal effect

\begin{lstlisting}
( x[7] x[8] -- x[7] x[9] )
\end{lstlisting}

can be presented as:

\begin{lstlisting}
( x1 x2 -- x1 x3 )
\end{lstlisting}

This shows that the second element from the top is the second input (x1).  By contrast, an output
such as \texttt{( x x -- x x )} hides that relationship.

The current artifact keeps an identifier visible if it was written explicitly
in a source specification or if the corresponding identity occurs more than
twice in the working data.  An automatically created identity occurring once
or twice may be printed without an identifier.  The implementation also stores
that shortened effect for later use.  As a result, formatting can remove
information needed by a later composition.

There is no analysis benefit to this policy; its advantage is only shorter,
backward-compatible output.  A revised implementation should:

\begin{enumerate}
  \item retain all identity classes in dictionary entries;
  \item renumber them consecutively when an effect is displayed;
  \item omit suffixes only when the Forth convention remains unambiguous.
\end{enumerate}

\section{Branches and Control-Flow Joins}
\label{sec:branches}

A branch creates two possible stack states.  Code after the branch needs one
interface.  Matching stack depth is not sufficient: one arm may leave an
address where the other leaves a number, or the arms may preserve different
input values.

A checker has several options.  It can retain a set of path-specific effects,
compute a safe effect that forgets some facts, require programmer annotations,
or reject programs for which it cannot construct one interface.  The current
checker uses a partial syntactic operation named \texttt{glb} in the source.
The name comes from earlier order-theoretic work, but the implementation should
be understood through the algorithm below rather than through lattice
terminology.

\subsection{Equal visible depths}

When both effects have the same number of inputs and outputs, the checker
aligns corresponding positions.  Each pair must have compatible types.  The
same global identifier replacement used for straight-line composition is then
applied.

For example, these two store-like effects can be combined:

\begin{lstlisting}
( X a-addr -- )
( X c-addr -- )
\end{lstlisting}

The common interface requires \texttt{a-addr}, because it is the more specific
address type accepted by both declarations.  The declared effect
\texttt{IF ( flag -- )} is composed separately and accounts for the selector.

\subsection{Unequal visible depths}

Effects of different displayed depths can still describe compatible behavior
because each effect omits an unchanged deeper prefix.  Let the first effect
show \texttt{k} more inputs than the second.  A join is possible only if it
also shows exactly \texttt{k} more outputs.  Those extra deep cells must be
preserved by the longer effect.  The remaining input and output positions are
then compared with the shorter effect.

For example:

\begin{lstlisting}
longer:   ( X[1] n -- X[1] char )
shorter:  (      n --      char )
\end{lstlisting}

The longer effect makes one cell of the implicit prefix visible.  It preserves
that cell, and its remaining \texttt{n -- char} behavior agrees with the
shorter effect.  The common interface is the longer effect.

The following pair is incompatible:

\begin{lstlisting}
( X -- X X )
(   --     )
\end{lstlisting}

The input-depth difference is one, but the output-depth difference is two.
This is why \texttt{IF DUP THEN}, with no matching \texttt{ELSE}, is rejected:
only one runtime path leaves the extra item.

The intended algorithm compares the shorter effect with the remaining slices
of the longer effect after the \texttt{k}-cell prefix.  The current native
helper starts this final comparison at vector offset zero instead of offset
\texttt{k}.  It can therefore reject a valid unequal-depth join when the
prefix and the remaining suffix have different types.  This is an
implementation defect, not part of the intended rule.

\subsection{The \texttt{MAYSWAP} example}

Consider:

\begin{lstlisting}
: MAYSWAP  IF SWAP THEN ;
\end{lstlisting}

The true arm swaps two cells; the false arm preserves them.  A standard
single-effect summary that makes no unsupported identity claim is:

\begin{lstlisting}
( X1 X2 flag -- X3 X4 )
\end{lstlisting}

A more precise analysis would retain two alternatives: the outputs are either
\texttt{X2 X1} or \texttt{X1 X2}.  The current syntactic join instead forces
the two inputs into one identity and reports:

\begin{lstlisting}
( X[1] X[1] flag -- X[1] X[1] )
\end{lstlisting}

That is not the general effect of \texttt{MAYSWAP}.  It demonstrates why
unifying branch variables is not automatically a sound summary of both
runtime paths.  A soundness result would need a defined meaning for primitive
effects, explicit rules for input and output constraints, and either a safe
loss of information or a representation of alternative effects.

\section{Loop Invariants}
\label{sec:loops}

A loop introduces a back edge.  The stack state produced by one pass must be
valid at the next pass, and the state reported after the loop must cover every
possible exit.

A conventional data-flow analyzer maintains an abstract stack at the loop
header, propagates it through the body, merges the result back at the header,
and repeats until the state stops changing.  That process computes a fixed
point \cite{cousot1977}.  Another design is to require a declared loop
interface and check every back edge against it.

The current evaluator uses a smaller local test:

\begin{lstlisting}
onePass = effect(body)
twoPass = compose(effect(body), effect(body))
summary = commonEffect(onePass, twoPass)
\end{lstlisting}

This test terminates immediately and detects every nonzero net stack-depth
change: if one pass changes the depth by one cell, two passes change it by two,
so their interfaces cannot agree.  The test does not establish that the
returned identity relationships hold after every number of passes.

\subsection{Counterexample}

The limitation can be shown with one data-cell type and two synthetic words:

\begin{lstlisting}
P      ( X[1] X[2] -- X[3] X[1] )
NEXT?  ( -- flag )
UNTIL  ( flag -- )
\end{lstlisting}

\texttt{NEXT?} supplies a termination flag.  It is immediately consumed by
\texttt{UNTIL}, so one complete loop pass has the data-stack effect of
\texttt{P}.

Using symbolic values, repeated \texttt{P} executions behave as follows:

\begin{lstlisting}
input:         A B
one pass:      C A
 two passes:   D C
three passes:  E D
\end{lstlisting}

Only one pass preserves the original lower input in the top result.  The
two-pass and three-pass effects contain no output tied to either original
input.  Nevertheless, the current join can identify an unrelated two-pass
variable with the original input.  It accepts:

\begin{lstlisting}
: TEST  BEGIN P NEXT? UNTIL ;
\end{lstlisting}

and reports:

\begin{lstlisting}
TEST ( X[2] X[1] -- X[3] X[2] )
\end{lstlisting}

This report is equivalent, after renaming, to the one-pass relationship.
Composing the reported summary with itself loses that relationship, so the
summary is not stable.  A checker requiring an inductive loop interface would
reject this candidate or weaken it to an interface with no input/output
identity claim.

This example gives the precise limitation.  The one-versus-two rule is useful
for depth checking, but it is not a proof that the returned typed data-flow
summary covers arbitrary iteration counts.

\section{Processing Forth Source}
\label{sec:source}

Stack-effect composition alone cannot process Forth source.  Some words consume
the next name, scan to a delimiter, start a definition, end a definition, or
execute immediately during compilation.  The specification format records
these roles:

\begin{lstlisting}
"("      parse until ")"          ( -- )
CONSTANT parse word define        ( X -- )
VARIABLE parse word define        ( -- a-addr )
:        parse word define colon  ( -- )
;        control end              ( -- )
IF       control if               ( flag -- )
literal integer                   ( -- n )
\end{lstlisting}

Ordinary comments are consumed but are not trusted as type declarations.
Thus a source comment such as \texttt{( -- n )} cannot override an inferred
effect.  A recognized locals declaration may provide a provisional definition
shape, but that is a separate parser feature.

\subsection{Declarative control structures}

Control syntax can be described by a source pattern and an effect recipe.  The
demo spelling \texttt{FI} is a synonym for the usual \texttt{THEN}:

\begin{lstlisting}
syntax:
  IF <then branch> [ELSE <else branch>] FI
effect:
  IF
  either <then branch> <else branch>
\end{lstlisting}

The recipe language has three important operations: sequence captured regions,
combine two alternatives, and apply the one-versus-two test to a repeated
region.  Bare control words contribute their declared runtime data-stack
effects.  Parser behavior and data-stack behavior therefore remain separate
from the combination algorithms.

\subsection{The compile-time control-flow stack}

A control word has both a runtime role and a compilation role.  At runtime,
\texttt{IF} consumes a flag.  During compilation, the Forth standard describes
\texttt{IF} as producing an \texttt{orig} item on the control-flow stack;
\texttt{THEN} resolves that item \cite{forth2012}.

The current checker records \texttt{( flag -- )} as the runtime data-stack
effect and records \texttt{control if} as parser metadata.  Structural parsing
catches missing or misnested delimiters, but it does not represent the
control-flow stack as a second typed stack.  A future extension could assign
compile-time effects over items such as \texttt{orig}, \texttt{dest}, and
\texttt{do-sys}, independently of runtime data-stack effects.

\section{Complete Example}
\label{sec:example}

The bundled \texttt{real} profile consists of:

\begin{itemize}
  \item \path{ex1types.txt}, containing types and subtype edges;
  \item \path{ex1specs.txt}, containing word and parser specifications;
  \item \path{ex1prog.txt}, containing the checked source.
\end{itemize}

Run it from the artifact root with:

\begin{lstlisting}
./run-evaluator-gforth.sh real
\end{lstlisting}

\subsection{Representative profile entries}

The type declarations include \texttt{X}, \texttt{n}, \texttt{char},
\texttt{flag}, \texttt{addr}, \texttt{c-addr}, and \texttt{a-addr}.  Relevant
word declarations are:

\begin{lstlisting}
DUP      ( X[1] -- X[1] X[1] )
SWAP     ( X[2] X[1] -- X[1] X[2] )
literal integer ( -- n )
IF       control if ( flag -- )
ELSE     control else ( -- )
FI       control fi ( -- )
BEGIN    control begin ( -- )
WHILE    control while ( flag -- )
REPEAT   control repeat ( -- )
UNTIL    control until ( flag -- )
DP       ( -- a-addr )
@        ( a-addr -- X )
C@       ( c-addr -- char )
0=       ( n -- flag )
\end{lstlisting}

\texttt{DP} is a system-specific demo word for the data-space or dictionary
pointer.  It is not assumed by the checker; its \texttt{( -- a-addr )} effect
is explicitly declared.

The current specification dictionary accepts one effect per word.  It cannot
directly declare both \texttt{0= ( n -- flag )} and
\texttt{0= ( u -- flag )}.  A profile can instead use a shared accepted type.
The bundled Forth-2012-like profile declares \texttt{0= ( x -- flag )}, which
accepts both signed and unsigned cells.  A stricter profile can introduce an
\texttt{integer} supertype above \texttt{n} and \texttt{u}.  Direct support
for multiple effects or overload selection would preserve more precision.

\subsection{Program and output}

The program defines five words and checks one top-level phrase:

\begin{lstlisting}
: PEEK2 DUP @ SWAP @ ;
: MAYSWAP IF SWAP FI ;
: NLOOP BEGIN DUP 0= WHILE REPEAT ;
: ULOOP BEGIN DUP 0= UNTIL ;
: KEEPIF IF DUP ELSE DUP FI ;

DP DP C@ 0= KEEPIF
\end{lstlisting}

The exact native log contains:

\begin{lstlisting}
PEEK2   ( a-addr[1] -- X[2] X )
MAYSWAP ( X[1] X[1] flag -- X[1] X[1] )
NLOOP   ( n[1] -- n[1] )
ULOOP   ( n[1] -- n[1] )
KEEPIF  ( X[1] flag -- X[1] X[1] )
\end{lstlisting}

The \texttt{MAYSWAP} line is retained to make the artifact output
reproducible, but Section~\ref{sec:branches} explains why it is too
restrictive.  Its general single-effect interface should not claim that all
four \texttt{X} positions hold one value.

The top-level trace ends with:

\begin{lstlisting}
DP      ( -- a-addr[1] )
DP      ( -- a-addr )
C@      ( a-addr -- char )
0=      ( char -- flag )
KEEPIF  ( a-addr[1] flag -- a-addr[1] a-addr[1] )
< a-addr[1] a-addr[1]
\end{lstlisting}

\texttt{C@} requires \texttt{c-addr}; \texttt{DP} provides the more specific
\texttt{a-addr}, so matching succeeds.  In this profile \texttt{char} is a
subtype of \texttt{n}, so \texttt{0=} accepts the result.  \texttt{KEEPIF}
consumes the flag and duplicates the surviving address on either branch.

\section{Computing Process}
\label{sec:implementation}

After one non-recursive source body has been parsed, its evaluation is a
post-order traversal of a finite syntax tree:

\begin{itemize}
  \item a leaf obtains an effect from word lookup or literal classification;
  \item a sequence node invokes straight-line composition;
  \item a branch node invokes the common-effect operation;
  \item a repetition node invokes the one-versus-two operation.
\end{itemize}

Every node depends only on its children, and each implemented operation is
deterministic.  The parsed body therefore has one implementation result: an
effect or a clash.  This is a characterization of the program executed by the
checker, not a type-soundness theorem.  It does not prove that primitive
specifications match runtime behavior, and it does not cover unrestricted
recursion, dynamic execution, or all dictionary construction.

The native implementation is the single source file
\path{gforth-evaluator.fs}.  Its main components are organized by prefix:

\begin{itemize}
  \item \texttt{ev-ts-*}: types, aliases, and subtype relationships;
  \item \texttt{ev-sym-*}: typed cells and symbolic identifiers;
  \item \texttt{ev-spec-*}: stack effects and the three combination algorithms;
  \item \texttt{ev-ss-*}: specification dictionary;
  \item \texttt{ev-sc-*} and \texttt{ev-parse-*}: scanning and source parsing;
  \item \texttt{ev-diag-*} and \texttt{ev-log-*}: diagnostics and logs.
\end{itemize}

Effects are mutable records.  Dictionary effects are deep-cloned before use,
independent branches receive disjoint identifier ranges, and input line
endings are normalized.  These details prevent one analysis from changing a
later dictionary lookup.

Boundary matching is linear in the shorter touching boundary, but every match
currently substitutes through complete working vectors.  Large intermediate
effects can therefore make reduction roughly quadratic in effect size.  A
union--find structure for identifier classes would reduce repeated copying.

\section{Related Work}
\label{sec:related}

\paragraph{Forth stack effects.}
The Forth standard uses stack comments and numeric suffixes but does not make
every comment a static judgment \cite{forth2012,rather1996}.  Earlier work by
the present author developed algebraic composition, multiple effects, typed
wildcards, inheritance, and must-analysis operators
\cite{poial1991,poial1992,poial1994,poial2002,poial2006}.  The current artifact
combines a subset of those mechanisms with source parsing, external control
declarations, inferred definitions, and diagnostics.  Its input format is less
expressive than the earlier multiple-effect work because it currently accepts
one effect per word.

\paragraph{StrongForth.}
StrongForth, developed by Stephan Becher, integrates static typing into a Forth
system.  Recent articles cover object-oriented typing, programming practice,
and word overloading
\cite{becher2025objects,becher2025practice,becher2025overloading}.  Overloading
is relevant to words such as \texttt{0=} and \texttt{EXECUTE}, where one broad
common type loses distinctions.  StrongForth targets a typed Forth dialect;
the present checker leaves the target system unchanged and applies an
external profile.  StrongForth therefore demonstrates that limitations of the
current artifact are not inherent limitations of Forth syntax.

\paragraph{Optional and pluggable Forth typing.}
Riegler's thesis presents a Haskell prototype with optional checkers ranging
from stack underflow and overflow checks to stronger static type consistency
\cite{riegler2015}.  It covers subtyping, control structures, reference types,
multiple stack effects, compile-time programming, object orientation, and
higher-order programming.  The present artifact adds a native Gforth
implementation, external parser and control profiles, and source-oriented
traces, but is narrower in multiple effects, compile-time stack typing, and
higher-order features.

\paragraph{Other stack-machine type systems.}
Stoddart and Knaggs study type inference for stack-based languages
\cite{stoddart1993}.  Saabas and Uustalu give compositional systems for
stack-based low-level code \cite{saabas2006}.  Their instruction languages are
more fixed than Forth source and do not need to model an open-ended outer
interpreter in which words consume source text or create definitions.  A fixed
instruction set makes conventional typing rules and soundness arguments easier
to state.

\paragraph{WebAssembly.}
The current online WebAssembly Core Specification identifies itself as Release
3.0, dated 23 July 2026 \cite{wasm3}.  WebAssembly does not infer a loop
interface by comparing one and two body executions.  A block type declares the
operand types consumed and produced.  A control stack records each active
block's label type and stack height, and every branch is checked against its
target label.  A loop back edge therefore targets a declared loop-label input.
WebAssembly also defines controlled stack polymorphism for unreachable code
and has substantial mechanized metatheory \cite{watt2018,mcdermott2022}.

This comparison locates the trade-off.  WebAssembly obtains stronger branch
and loop guarantees from fixed control syntax and explicit block interfaces.
The present Forth checker tries to infer interfaces from source while loading
parser and control behavior as data.  Retargetability and source-level Forth
support are benefits; lossy normalization, the syntactic branch join, and the
one-versus-two loop rule are costs of this implementation strategy.

\paragraph{Higher-order concatenative code.}
A generic stack-prefix parameter stands for any unchanged sequence below a
word's visible operands.  A first-class quotation is a value that itself has a
stack transformation.  Some higher-order words require a quotation that works
for every possible stack prefix.  In type-system terminology, the generic
parameter then appears inside a function argument type; this is often called
higher-rank, or rank-2, polymorphism.  The term describes where the generic
parameter is introduced, not the number of stack cells.

A recent account of the IV language avoids automatic inference of these nested
generic types by requiring definition annotations and explicit parameters for
execution and composition operators \cite{dinikeev2025}.  The current checker
has an implicit unchanged prefix but no quotation type and no general
algorithm for prefix variables.  Supporting first-class quotations therefore
requires an extension of the type language, not another primitive word entry.

\section{Limitations and Next Steps}

The current implementation has the following known limits:

\begin{itemize}
  \item Primitive and parser specifications are trusted.  An incorrect
        declaration can make a program appear valid.
  \item Only equal or subtype-related boundary types match; one word cannot
        yet have several alternative primitive effects.
  \item Normalization can remove identity relationships that later checks
        need.
  \item Branch joining can impose unsupported identity constraints, as
        \texttt{MAYSWAP} shows.  The unequal-depth implementation also uses the
        wrong comparison offset in some cases.
  \item Loop checking compares one pass with two and does not compute an
        inductive header state.
  \item Compile-time control-flow items are parsed structurally but are not
        represented as typed stack effects.
  \item Return-stack manipulation, unrestricted \texttt{EXECUTE}, non-local
        \texttt{THROW}, self-modifying definitions, and unrestricted
        metaprogramming require additional models.
  \item Recursive dictionary construction and general forward references are
        outside the deterministic parsed-body characterization.
  \item Two top-level negative regression cases are currently missed.
\end{itemize}

The immediate engineering priorities are to preserve identity classes
internally, adopt standard-style output, fix unequal-depth alignment, and
repair top-level clash reporting.  Subsequent extensions can add multiple
primitive effects, typed compile-time control items, explicit stack-prefix and
quotation types, branch alternatives, and fixed-point loop analysis.  A
semantic soundness result also requires an operational model for trusted
primitives and precise rules for input and output constraints.

\section{Conclusion}

This work describes a configurable source-level checker for Forth rather than
a general type system for every concatenative language.  Its core mechanisms
are subtype-aware boundary matching, symbolic value identifiers, and external
profiles for Forth words and parser behavior.  These mechanisms provide useful
checking for straight-line source and support reproducible inference for
non-recursive definitions.

Branches and loops require more than stack-depth equality.  The current
branch operator and one-versus-two loop test are executable experiments with
clearly identified limits, not substitutes for path-sensitive control-flow
analysis or inductive invariants.  The \texttt{MAYSWAP} and \texttt{P}
examples make those limits concrete.

The artifact is useful as executable stack-effect documentation and as a
platform for experiments with different Forth profiles.  Preserving identities
internally, supporting alternative effects and compile-time control items, and
using fixed-point loop analysis are direct steps toward stronger guarantees.
